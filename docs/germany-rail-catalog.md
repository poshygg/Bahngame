# Germany rail service snapshot

Checked on **13 September 2026**. This catalog is a bundled OpenStreetMap public-transport snapshot covering Germany's sixteen federal states and multiple urban rail networks. It includes DB and other operators. It is **not a live Deutsche Bahn journey-planning API, a timetable, or a complete national rail database**.

The custom journey graph may use consecutive stops of these mapped, directed service variants. A graph result means that a connection exists in this imported snapshot; it does not establish a departure time, operating day, fare, accessible interchange, platform, disruption status, or a currently bookable journey. Missing source connections must remain unavailable rather than being filled with geographically nearest stations.

## Sources and reuse

The station coordinates, names, route membership, stop order, service reference, network and operator tags come from **OpenStreetMap contributors**, retrieved through the [Overpass API](https://wiki.openstreetmap.org/wiki/Overpass_API). The [OSM public-transport model](https://wiki.openstreetmap.org/wiki/Public_transport) describes ordered stop positions/platforms and separate route variants. Every imported line retains its exact OSM relation URL; stations retain their contributing OSM object IDs and source URL. The raw cached responses are included alongside the importer so the transformation can be audited.

The OSM-derived database is made available under the [Open Database License 1.0](https://opendatacommons.org/licenses/odbl/1-0/), with attribution to [OpenStreetMap contributors](https://www.openstreetmap.org/copyright). Keep this attribution visible in the product and retain the license/source information when redistributing the catalog. Public distribution of a derivative database must satisfy the ODbL's applicable share-alike and access requirements; offer the data snapshot in reusable form with its license. This database license does not grant rights in DB logos, vehicle liveries, photographs, or unrelated artwork. Those questions are covered separately in [rail-services-and-rights.ko.md](rail-services-and-rights.ko.md).

State assignment uses the public-domain [Natural Earth 1:10m admin-1 boundaries](https://www.naturalearthdata.com/downloads/10m-cultural-vectors/10m-admin-1-states-provinces/), from the Germany subset generated by `scripts/import-german-regions.cjs`. These are display-scale boundaries, not cadastral boundaries. The full polygons in `artifacts/german-regions.geojson` are used for point-in-polygon classification. Stops outside Germany, or outside a generalized border polygon, may have no `stateId`; their order is retained rather than silently joining across an omitted stop. Some international services therefore include foreign endpoints.

The current [DB Open Data information page](https://data.deutschebahn.com/opendata) points to its successor portals and the API Marketplace. Station data alone does not prove a service connection. [DB Timetables](https://developers.deutschebahn.com/db-api-marketplace/apis/product/timetables) is a separate subscribed API with its own usage plan and CC BY 4.0 dataset terms. This build neither requires DB credentials nor claims to retrieve current DB API results.

## Catalog contract

`src/data/rail/catalog.ts` exports `RAIL_CATALOG`, `RAIL_STATIONS` and `RAIL_LINES`. Types are in `types.ts`. `catalog.generated.json` is the only large data file imported into the runtime; the game never contacts Overpass.

- `RailStation`: a canonical interchange ID, a source-backed primary station name, representative coordinates, aliases, contributing OSM IDs, and optional ISO 3166-2 state/city IDs.
- `RailLine`: one mapped direction/variant with an exact source relation URL, service `ref`, service category, optional operator/network, ordered station IDs, source member IDs, states/cities and check date.
- `RailCatalog.states`: all sixteen ISO identifiers, such as `DE-BE`, `DE-NW` and `DE-TH`, with English/German display names.
- `RailCatalog.cities`: thirty-two discovery centres. A station's city is a display grouping within the same state and 16 km of that centre. This proximity grouping **never creates route edges or interchange identities** and is not an assertion that every grouped stop is within the municipal boundary.

A relation ID, not just `RE9` or `U1`, identifies a variant. Service references in OSM can represent a route family or an individual service designation; do not treat every numeric reference as a unique national line number, train number, or vehicle model. All imported `bidirectional` values are false: reverse travel requires its own mapped directed relation. The operator string is source metadata and can be stale. Missing `dbOperator` means unverified, not false.

## Import selection and transformation

The national discovery query selects Germany-intersecting `type=route` relations with `route=train`, `subway`, `light_rail` or `tram`. Its initial index contains **3,376** relations: 2,113 train, 131 subway, 149 light rail and 983 tram. Only PTv2 relations with a service reference and without explicit proposed/disused flags are selected for the playable import.

The selected set includes mapped ICE/IC/EC variants, all discovered RE9 variants, mapped U-Bahn variants, and a balanced selection of local, RE, RB and S services for the discovery cities. This is a representative selection rather than all routes in every town. The final `import-report.json` records selected/imported/rejected counts, state and city coverage, and any unresolved members; `catalog.generated.json` carries the OSM snapshot timestamp.

The frozen import contains **5,073 canonical stations, 911 directed service variants and 16,406 source-ordered legs**, covering all **16 states** and **32 discovery cities**. Every discovery city has at least three distinct service references. Of 938 selected relations, 27 were excluded: 17 unresolved near-coincident stop/platform pairs, eight variants with unresolved named/location members, and two variants without German stops. The remaining 15 unresolved member references are recorded for a future source review; no missing intermediate stops were skipped to admit these variants. The national source index timestamp is **2026-09-12T18:18:21Z**. Detail responses were cached during this import and can have later individual timestamps.

The transformation preserves the source member order. Stops are canonicalized only through an actual OSM stop area/group, a spatially consistent matching UIC station reference, or the PTv2 adjacent stop/platform pair whose names are compatible and coordinates pass a small sanity bound. The spatial checks corroborate explicit source evidence; they do not discover arbitrary transfers by distance. Stop-area-group names may list multiple neighbouring stops, so an actual member station's source name is used as the primary typing name and the other names are kept as aliases.

**Matching UIC tags are not sufficient on their own.** Before a UIC-based union, both existing source clusters must have coordinates and their combined diameter must be at most 3 km. The cached source contains five conflicting copied identifiers: Schwetzingen/Stuttgart-Ebitzweg, Düsseldorf Zoo/Westerland, Berlin-Hohenschönhausen/Kersbach, Steinpleis/Stuttgart Schwabstraße, and Griebnitzsee/Kiel-Elmschenhagen. These are kept separate, with the rejected union evidence in `import-report.json`. A second audit checks every final source cluster, including identities established through explicit stop areas/groups and role pairs. Any cluster over 3 km is excluded from the playable graph along with referencing variants, rather than bypassing its stops. All 6,267 source clusters passed after the five UIC unions were rejected; the largest playable interchange has a 0.509 km member-to-member extent under the validator's independent great-circle calculation. The 3 km limit is a conservative rejection threshold, not a walking-transfer time or guarantee of correct station identity.

Where a platform has an explicit fetched stop-area membership but no individual geometry, the same area's located members can corroborate its adjacent stop-position pair. Stop-position occurrences are authoritative when a platform represents the same canonical stop; platform-only stops and repeated stop-position visits remain in source order. This prevents a misplaced platform member from inventing a second visit. For example, OSM relation [71642](https://www.openstreetmap.org/relation/71642) appends its Mulhouse entry platform after Freiburg's exit stop; the imported `P11;RB 28` variant correctly remains Mulhouse–Bantzenheim–Neuenburg–Müllheim–Freiburg. A regression check covers this case.

Five reviewed interchange labels explicitly select existing source objects: [Berlin Hauptbahnhof](https://www.openstreetmap.org/relation/5688517), [München Hauptbahnhof](https://www.openstreetmap.org/relation/2063908), the generic [Frankfurt airport interchange](https://www.openstreetmap.org/relation/454147), [Köln Hauptbahnhof](https://www.openstreetmap.org/relation/3097360), and [Stuttgart-Untertürkheim](https://www.openstreetmap.org/relation/382671). This avoids assigning an entire connected interchange the name of just its underground or regional platforms. Köln's Dom/Hbf local-rail name remains a searchable alias rather than replacing the mainline name on ICE routes. Canonical interchange identity does not imply a zero-minute or step-free walking transfer.

Unknown names/coordinates, ambiguous near-coincident stop/platform pairs, absent route details and routes without German stops are excluded. Missing stops are **not** discarded from the middle of an accepted route. `sourceStopIds` records the member introducing each canonical stop so the route order can be validated against the cached relation.

The data does not provide railway-track geometry. Displaying a line between consecutive stop coordinates remains a schematic depiction of a real mapped service order, not an exact track trace. Existing landmark data is independent and should not be silently attached to another city because a national service has a similar stop name.

## Rebuild and checks

The cached raw index and detail files reproduce this particular import. In the workspace root, run:

```sh
node src/data/rail/import-osm.mjs fetch
node src/data/rail/build-catalog.mjs
node src/data/rail/recover-stops.mjs
node src/data/rail/build-catalog.mjs
node src/data/rail/validate-catalog.mjs
npm run typecheck
```

The fetch step resumes cached batches and requests only missing selected relation details. The recovery step retrieves explicitly referenced platform objects; it cannot repair inaccurate source mapping by guessing. Review `import-report.json` before replacing a released snapshot. The check date and discovery selection are versioned in `import-osm.mjs`; a future refresh should deliberately update them and the national raw index rather than quietly replacing a competition's content mid-season.

The importer makes sequential requests with an identifying User-Agent, caches results, and respects 30-second backoff on Overpass 406/429/504 responses. This follows the public instance's [documented usage policy](https://wiki.openstreetmap.org/wiki/Overpass_API#Public_Overpass_API_instances). A deployed game should continue using the bundled snapshot. Regular production refreshes or substantially larger imports need a suitable hosted service or local extract rather than one public request per player.

`validate-catalog.mjs` checks unique IDs, finite named station locations, all-state coverage, three or more refs in every discovery city, source member ownership/order, directedness, endpoint names, and the presence of RE9/ICE examples. It independently calculates every playable station cluster's geographic extent and checks that the five known conflicting UIC pairs remain separate. Other regressions cover RB11's Stuttgart-Ebitzweg stop, Köln's exact mainline-name source, the Mulhouse/Freiburg platform order and Berlin/Munich connectivity without a duplicated Südkreuz platform. These checks establish structural provenance; they do not independently certify that every community-mapped timetable variant is up to date.
